# مستندات فنی V2Ray Pool Intelligence Engine 2.0

**نسخه مستندات:** 1.0.0  
**وضعیت:** مشخصات معماری و قراردادهای پیشنهادی برای پیاده‌سازی  
**زبان:** فارسی  
**مدل استقرار هدف:** GitHub Actions + شاخه مستقل `data` + API استاتیک + GitHub Pages

## هدف

این بسته، معماری هدف سامانه را تعریف می‌کند. هدف سامانه فقط جمع‌آوری کانفیگ نیست. سامانه باید کانفیگ‌ها را دریافت، اعتبارسنجی، با Xray آزمایش، IP خروجی آن‌ها را بررسی، وضعیت ثابت یا چرخشی را تعیین، کیفیت را رتبه‌بندی و نتیجه را در اشتراک‌ها و API منتشر کند.

**اولویت محصول: اثبات پایداری IP خروجی.** سرعت و تأخیر در رتبه بعدی قرار دارند. سامانه نباید یک کانفیگ را فقط به دلیل یک تست موفق، ثابت اعلام کند.

## وضعیت و دامنه این مستندات

این فایل‌ها «مشخصات طراحی» هستند. وجود یک مسیر در نمودار معماری به معنی پیاده‌سازی آن نیست. هر قابلیت تا زمانی که کد، آزمون و خروجی معتبر آن وجود نداشته باشد، پیاده‌سازی‌شده محسوب نمی‌شود.

این مستندات ساختار هدف را مشخص می‌کنند؛ آن‌ها ZIP اجرایی پروژه یا گزارش ممیزی کد فعلی نیستند. قبل از پیاده‌سازی باید این قراردادها با کد موجود و قالب تاریخی شاخه `data` تطبیق داده شوند.

## اصول کلیدی

1. تشخیص IP ثابت باید بر چند اجرای مستقل و چند مشاهده‌گر IP تکیه کند.
2. هر مشاهده IP باید زمان، خانواده IP، منبع مشاهده و نتیجه اعتبارسنجی داشته باشد.
3. اختلاف مشاهده‌گرها نباید به‌عنوان IP ثابت تفسیر شود.
4. وضعیت کانفیگ و تاریخچه شواهد باید از هم جدا باشند.
5. فایل‌های اشتراک، API و داشبورد باید از یک مجموعه داده معتبر و یکسان تولید شوند.
6. انتشار باید اتمیک باشد و تاریخچه قبلی شاخه `data` را حفظ کند.
7. داده ورودی غیرقابل اعتماد است؛ دانلود، Parse و اجرای تست باید محدود و ایزوله باشد.
8. GitHub Actions موقعیت جغرافیایی ثابت و قابل انتخاب برای Runner عادی تضمین نمی‌کند.
9. هیچ مقدار اندازه‌گیری‌نشده‌ای نباید به‌عنوان latency، throughput، uptime یا امتیاز واقعی منتشر شود.

## ساختار شاخه داده

ساختار هدف شاخه `data` در سند `docs/02-data-tree-and-contracts.md` تعریف شده است. فایل‌های شاخه `data` خروجی عمومی هستند؛ هر محتوایی که در این شاخه قرار گیرد، باید عمومی فرض شود.

## ترتیب پیشنهادی پیاده‌سازی

1. ثبت قرارداد State و شناسه پایدار کانفیگ.
2. ساخت Collector و Validator امن.
3. ساخت Test Runner مبتنی بر Xray و ثبت شواهد IP.
4. ساخت طبقه‌بندی IP و سیاست‌های انتقال وضعیت.
5. ساخت معیارهای رتبه‌بندی بر اساس داده واقعی.
6. ساخت خروجی‌های اشتراک و JSON API.
7. ساخت داشبورد و Workflow انتشار اتمیک.
8. اجرای تست‌های پذیرش و مهاجرت تاریخچه قبلی.

## محدودیت مهم استقرار GitHub-only

جمع‌آوری جهانی منابع با اجرای GitHub Actions امکان‌پذیر است؛ اما این موضوع به معنی تست اتصال از همه کشورها نیست. Runner عادی GitHub محل خروجی قابل انتخاب و تضمین‌شده برای هر کشور ندارد. برای اندازه‌گیری منطقه‌ای باید Runner اختصاصی یا سرویس تست منطقه‌ای اضافه شود. تا آن زمان، کشور ثبت‌شده برای کانفیگ باید کشور **IP خروجی تونل** باشد، نه کشور Runner.

# ۰۰ — معرفی و دامنه سامانه

## ۱. مسئله‌ای که سامانه حل می‌کند

یک فهرست خام از URIهای V2Ray کیفیت یا پایداری را اثبات نمی‌کند. URI ممکن است از نظر نحوی معتبر باشد، اما سرور در دسترس نباشد. اتصال ممکن است برقرار شود، اما IP خروجی آن ثابت نباشد. حتی ممکن است IP در یک اجرا ثابت باشد و در اجرای بعدی تغییر کند.

سامانه باید این لایه‌ها را از هم جدا کند:

- **کشف:** منبع یک کانفیگ را معرفی می‌کند.
- **اعتبارسنجی:** ساختار و مقصد از نظر فنی و امنیتی قابل قبول است.
- **تست اتصال:** Xray می‌تواند تونل را برقرار کند.
- **تأیید IP خروجی:** یک یا چند مشاهده‌گر، IP خروجی را ثبت می‌کنند.
- **طبقه‌بندی:** شواهد چند اجرا نشان می‌دهد IP ثابت، چرخشی یا نامشخص است.
- **رتبه‌بندی:** کیفیت بر اساس اندازه‌گیری‌های واقعی محاسبه می‌شود.
- **انتشار:** اشتراک و API از داده تأییدشده ساخته می‌شوند.

## ۲. اهداف محصول

- حفظ و به‌روزرسانی یک مخزن جهانی از کانفیگ‌های عمومی.
- حذف ورودی‌های خراب، تکراری و ناامن.
- تست واقعی با Xray Core.
- شناسایی IP خروجی هر کانفیگ.
- جداسازی اشتراک Fixed از Rotating.
- رتبه‌بندی سریع‌ترین و متعادل‌ترین کانفیگ‌ها با معیارهای قابل ردیابی.
- ارائه خروجی متنی سازگار با کلاینت‌های اشتراک.
- ارائه API استاتیک و داشبورد مدیریتی.
- نگهداری State و History میان اجراهای GitHub Actions.

## ۳. موارد خارج از دامنه نسخه GitHub-only

- تضمین تست از همه کشورها.
- تضمین uptime پیوسته در تمام ساعات، مگر با اجرای مکرر و مستقل.
- تضمین مالکیت یا کنترل IP خروجی توسط منتشرکننده.
- تضمین ناشناس‌ماندن یا امنیت عملیاتی ارائه‌دهنده کانفیگ.
- اجرای سرویس Backend زنده؛ API نسخه اول فایل JSON استاتیک است.
- نگهداری محرمانه کانفیگ‌هایی که قرار است در اشتراک عمومی منتشر شوند.

## ۴. تعریف معیار موفقیت

نسخه قابل قبول باید بتواند برای هر کانفیگ منتشرشده این موارد را پاسخ دهد:

1. شناسه پایدار کانفیگ چیست؟
2. پروتکل و وضعیت فعلی آن چیست؟
3. آخرین تست موفق در چه زمانی انجام شده است؟
4. IP خروجی مشاهده‌شده چیست و IPv4 است یا IPv6؟
5. چند مشاهده‌گر مستقل نتیجه را تأیید کرده‌اند؟
6. در چند اجرای مستقل همان IP مشاهده شده است؟
7. آیا شواهد کافی برای `FIXED_VERIFIED` وجود دارد؟
8. اگر IP تغییر کرده، چه زمانی و به چه IPای تغییر کرده است؟
9. latency و throughput از کدام آزمون آمده‌اند؟
10. چرا این کانفیگ در این رتبه قرار گرفته است؟

## ۵. اصول داده

- زمان‌ها در State و API با UTC و قالب ISO 8601 ذخیره شوند.
- همه رکوردها دارای `schema_version` باشند.
- هر Run دارای `run_id` یکتا باشد.
- مقادیر ناموجود `null` باشند؛ مقدار صفر به معنی مقدار اندازه‌گیری‌شده صفر است و نباید جایگزین null شود.
- داده خام مشاهده‌شده از داده مشتق‌شده جدا باشد.
- History به‌صورت append-only نگهداری شود؛ State آخرین تصویر معتبر باشد.

# ۰۱ — معماری سامانه

## ۱. نمای کلان

سامانه یک Pipeline دسته‌ای است. GitHub Actions آن را اجرا می‌کند. موتور داده را پردازش می‌کند. خروجی به شاخه `data` منتشر می‌شود. داشبورد استاتیک، فایل‌های JSON را می‌خواند.

```text
Sources
  │
  ▼
Collector ──► Parser / Normalizer / Deduplicator
  │
  ▼
Validator
  │
  ▼
Xray Tester ──► Connectivity / IP Observers / Metrics
  │
  ▼
Intelligence Engine
  ├── IP Tracker
  ├── Stability Classifier
  └── Ranking Engine
  │
  ▼
Distribution Builder
  ├── Subscription TXT
  ├── Country / Protocol TXT
  └── Static JSON API v1
  │
  ▼
History + State + Dashboard Data
  │
  ▼
Atomic publish to data branch
```

## ۲. ساختار ماژولار موتور

```text
engine/
├── collector/
│   ├── sources.py       # رجیستری منابع فعال و سیاست هر منبع
│   ├── fetcher.py       # دریافت HTTP با محدودیت و کنترل Redirect
│   ├── parser.py        # تشخیص فرمت و استخراج URIها
│   └── normalizer.py    # پاک‌سازی و استانداردسازی URI
├── validator/
│   ├── syntax.py        # اعتبارسنجی URI و فیلدهای پروتکل
│   ├── security.py      # سیاست مقصد، IP و منابع محلی
│   └── tcp.py           # اتصال TCP کنترل‌شده به مقصد
├── tester/
│   ├── xray.py          # نصب/اجرای نسخه Pin شده Xray
│   ├── connectivity.py  # بررسی برقراری Tunnel
│   ├── ip_observers.py  # دریافت IP خروجی از چند مشاهده‌گر
│   ├── latency.py       # اندازه‌گیری تأخیر
│   ├── throughput.py   # سنجش نرخ انتقال با سقف مصرف
│   └── uptime.py        # محاسبه دسترس‌پذیری از Runهای مستقل
├── intelligence/
│   ├── ip_tracker.py    # ثبت شواهد IP
│   ├── stability.py     # محاسبه پایداری و انتقال وضعیت
│   ├── classification.py# Fixed / Rotating / Unknown
│   └── ranking.py       # امتیازدهی و ترتیب خروجی
├── distribution/
│   ├── subscriptions.py # ساخت فایل‌های TXT
│   ├── api.py           # ساخت JSON API v1
│   ├── country.py       # گروه‌بندی بر اساس کشور IP خروجی
│   └── protocol.py      # گروه‌بندی بر اساس پروتکل
└── core/
    ├── config.py        # بارگذاری و اعتبارسنجی تنظیمات
    ├── state.py         # خواندن/نوشتن State
    ├── scheduler.py     # تعیین کارهای Run
    ├── pipeline.py      # هماهنگ‌کننده مراحل
    └── publisher.py     # انتشار امن و اتمیک
```

وجود این نام‌ها یک قرارداد معماری است. پیاده‌سازی می‌تواند فایل‌ها را تا زمانی که مرز مسئولیت‌ها حفظ شود، بازآرایی کند.

## ۳. مسئولیت هر لایه

### Collector

فقط داده را دریافت و استخراج می‌کند. Collector نباید درباره ثابت یا چرخشی بودن IP تصمیم بگیرد.

### Validator

ورودی را از نظر ساختار، سیاست امنیتی و دسترسی TCP بررسی می‌کند. موفقیت Validator به معنی موفقیت Tunnel نیست.

### Tester

Xray را اجرا می‌کند و شواهد اتصال، IP خروجی و کیفیت را تولید می‌کند. هر Test باید دارای زمان شروع/پایان، Run ID، نسخه Xray و نتیجه باشد.

### Intelligence

شواهد چند Run را تحلیل می‌کند. این لایه حق ندارد نتیجه مشاهده‌نشده بسازد. طبقه‌بندی باید قابل توضیح و قابل بازتولید باشد.

### Distribution

از Snapshot معتبر، اشتراک و JSON ایجاد می‌کند. هیچ آزمون شبکه‌ای در Distribution اجرا نمی‌شود.

### Core

ترتیب مراحل، تنظیمات، State، زمان‌بندی و انتشار را مدیریت می‌کند.

## ۴. ترتیب Pipeline

1. بارگذاری تنظیمات و بررسی نسخه Schema.
2. دریافت آخرین State از شاخه `data`.
3. بازیابی منابع و جمع‌آوری داده.
4. Parse، Normalize و Deduplicate.
5. اعتبارسنجی Syntax و Security.
6. تست TCP و سپس اجرای Xray.
7. آزمون IP خروجی با مشاهده‌گرها.
8. اندازه‌گیری کیفیت در صورت موفقیت اتصال.
9. ادغام شواهد جدید با History قبلی.
10. محاسبه وضعیت و رتبه‌بندی.
11. تولید فایل‌های Sub، API و History.
12. اعتبارسنجی همه خروجی‌ها.
13. نوشتن اتمیک و انتشار به شاخه `data`.

اگر مرحله‌ای شکست بخورد، Pipeline باید مرحله و علت را ثبت کند. شکست یک منبع نباید باعث حذف داده سالم منابع دیگر شود.

## ۵. قرارداد بین ماژول‌ها

هر ماژول باید ورودی و خروجی مشخص داشته باشد. خروجی مراحل نباید به شکل متغیرهای سراسری یا فایل موقت بدون قرارداد منتقل شود. شناسه `config_id` در تمام مراحل ثابت می‌ماند. شواهد تست با `run_id` و `test_id` به کانفیگ وصل می‌شوند.

## ۶. قابلیت اطمینان

- هر Stage قابل اجرای مجدد باشد.
- تکرار یک Run نباید رکورد تکراری تولید کند؛ برای این کار از `run_id` و کلید idempotency استفاده شود.
- فایل خروجی ابتدا در مسیر موقت ساخته و اعتبارسنجی شود.
- سپس با Rename اتمیک جایگزین شود.
- انتشار شاخه `data` فقط پس از موفقیت تست‌های خروجی انجام شود.
- `git push --force` برای انتشار عادی ممنوع است.

# ۰۲ — ساختار شاخه data و قرارداد فایل‌ها

## ۱. درخت هدف

```text
data/
├── sub/
│   ├── main.txt
│   ├── fixed.txt
│   ├── fixed-verified.txt
│   ├── fixed-top50.txt
│   ├── rotating.txt
│   ├── rotating-top50.txt
│   ├── fastest.txt
│   ├── balanced.txt
│   ├── country/<ISO-3166-1-alpha-2>.txt
│   └── protocol/{vless,vmess,trojan,ss}.txt
├── api/v1/
│   ├── stats.json
│   ├── configs.json
│   ├── fixed.json
│   ├── rotating.json
│   ├── countries.json
│   └── rankings.json
├── history/
│   ├── daily/YYYY-MM-DD.json
│   ├── weekly/YYYY-Www.json
│   └── monthly/YYYY-MM.json
├── state/
│   ├── configs.json
│   ├── ip-history.json
│   └── metrics.json
└── README.md
```

فایل‌های روزانه/هفتگی/ماهانه با نام تاریخ UTC ساخته می‌شوند. فایل‌های State همیشه Snapshot جاری هستند. فایل‌های History نباید با Snapshot جاری جایگزین شوند.

## ۲. قواعد عمومی

- متن: UTF-8.
- زمان: UTC در قالب ISO 8601 با پسوند `Z`.
- JSON: UTF-8، بدون کامنت، با کلیدهای ثابت و `schema_version`.
- ترتیب آرایه‌ها: در خروجی‌های رتبه‌بندی، ترتیب از بهترین به ضعیف‌ترین است.
- مقدار نامعلوم: `null`، نه رشته خالی و نه صفر.
- شناسه: `config_id` از نوع `sha256:<hex>`.
- کشور: کد ISO 3166-1 alpha-2 با حروف بزرگ. `XX` فقط برای کشور نامشخص است و نباید فایل `country/XX.txt` به‌عنوان کشور واقعی منتشر شود.
- پروتکل: `vless`, `vmess`, `trojan`, `ss`. پروتکل ناشناخته نباید در یکی از این گروه‌ها قرار گیرد.
- همه فایل‌ها باید در هر انتشار از یک Snapshot واحد تولید شوند.

## ۳. قرارداد فایل‌های اشتراک

همه فایل‌های `sub/*.txt` فهرست Subscription هستند. فرمت پیش‌فرض انتشار باید از تنظیم `subscription.encoding` پیروی کند. مقدار پیشنهادی `base64` است: ابتدا URIهای معتبر به ترتیب مقرر، با یک URI در هر خط UTF-8 ساخته می‌شوند؛ سپس کل متن به Base64 استاندارد تبدیل می‌شود. Base64 بدون شکست خط نوشته می‌شود.

سازگاری با فرمت فعلی مخزن باید پیش از مهاجرت بررسی شود. اگر کلاینت‌های فعلی به متن خام نیاز دارند، `plain` به‌عنوان تنظیم جایگزین تعریف می‌شود. در یک انتشار، همه فایل‌های Subscription باید از یک Encoding استفاده کنند. فایل خالی باید صفر بایت باشد؛ رشته ساختگی یا URI نمونه مجاز نیست.

### `sub/main.txt`

تمام کانفیگ‌هایی که حداقل شرایط انتشار عمومی را دارند. موارد `QUARANTINED`، `INVALID`، `EXPIRED` و `IP_UNVERIFIED` پرریسک از این فایل حذف می‌شوند. سیاست ورود `ROTATING` و `UNSTABLE` باید در تنظیمات صریح باشد؛ پیش‌فرض محافظه‌کارانه، حذف `UNSTABLE` است.

### `sub/fixed.txt`

کانفیگ‌های طبقه‌بندی‌شده در `FIXED_CANDIDATE` یا `FIXED_VERIFIED`. نام این فایل نباید به‌عنوان تضمین قطعی خوانده شود. برای مصرفی که IP ثابت الزامی دارد، از `fixed-verified.txt` استفاده شود.

### `sub/fixed-verified.txt`

فقط کانفیگ‌هایی با وضعیت `FIXED_VERIFIED`. این فایل، خروجی اصلی برای نیاز IP ثابت است. هر رکورد باید شواهد کافی و به‌روز داشته باشد.

### `sub/fixed-top50.txt`

حداکثر ۵۰ کانفیگ `FIXED_VERIFIED` با بالاترین امتیاز Fixed. اگر کمتر از ۵۰ مورد وجود دارد، فقط موارد موجود نوشته می‌شوند.

### `sub/rotating.txt`

فقط کانفیگ‌هایی که تغییر IP آن‌ها با شواهد چند Run تأیید شده است. یک اختلاف موقت در مشاهده‌گرها به معنی Rotating نیست؛ آن حالت `IP_UNVERIFIED` است.

### `sub/rotating-top50.txt`

حداکثر ۵۰ کانفیگ Rotating، مرتب‌شده با امتیاز مناسب این گروه. این رتبه‌بندی نباید با رتبه‌بندی Fixed ادغام شود.

### `sub/fastest.txt`

کانفیگ‌های دارای اندازه‌گیری معتبر Latency، مرتب‌شده بر اساس زمان پاسخ. کانفیگ بدون داده Latency نباید در صدر قرار گیرد. بهتر است فقط نتایج تازه‌تر از حد `metrics.max_age` استفاده شوند.

### `sub/balanced.txt`

کانفیگ‌های دارای امتیاز متوازن بر اساس چند معیار اندازه‌گیری‌شده؛ برای نمونه latency، throughput، موفقیت اتصال و پایداری. وزن‌ها از تنظیمات خوانده می‌شوند. نبود یک معیار باید طبق سیاست وزن‌دهی مدیریت شود و نباید با عدد ساختگی جایگزین شود.

### `sub/country/<CC>.txt`

گروه‌بندی بر اساس کشور GeoIP مربوط به **IP خروجی تونل**. مکان سرور مقصد یا محل Runner معیار این دسته‌بندی نیست. داده GeoIP باید دارای نام پایگاه داده و زمان بررسی باشد.

### `sub/protocol/<protocol>.txt`

گروه‌بندی بر اساس پروتکل استخراج‌شده از URI و تأییدشده در Parser. این گروه‌بندی مستقل از Fixed/Rotating است.

## ۴. قرارداد API

تمام فایل‌های `api/v1/*.json` باید این فیلدهای پایه را داشته باشند:

| فیلد | نوع | توضیح |
|---|---|---|
| `schema_version` | string | نسخه Schema، مانند `1.0.0` |
| `generated_at` | string | زمان تولید UTC |
| `run_id` | string | شناسه اجرای تولیدکننده |
| `source_commit` | string/null | Commit کد موتور |
| `data_commit` | string/null | Commit داده‌ای که Snapshot از آن ساخته شده است |
| `data_age_seconds` | integer | فاصله تولید داده تا زمان انتشار |

### `stats.json`

خلاصه تعداد کل کانفیگ‌ها، تعداد هر وضعیت، پروتکل‌ها، کشورها، موفقیت تست‌ها، سن داده و زمان آخرین Run. تعدادها باید با `configs.json` و فایل‌های اشتراک سازگار باشند.

### `configs.json`

فهرست کانفیگ‌های قابل انتشار و metadata عمومی آن‌ها. هر مورد شامل شناسه، پروتکل، وضعیت، IP خروجی تأییدشده یا null، خانواده IP، کشور خروجی، آخرین تست، معیارهای کیفیت و URI عمومی است.

> شاخه `data` و API عمومی هستند. URI شامل UUID، Password یا Credential اتصال است. فقط کانفیگ‌هایی را منتشر کنید که انتشار عمومی آن‌ها مجاز است.

### `fixed.json`

فهرست `FIXED_CANDIDATE` و `FIXED_VERIFIED` با فیلد `verification_level` و تعداد شواهد. فیلد وضعیت باید صریح باشد.

### `rotating.json`

فهرست کانفیگ‌های `ROTATING` همراه با مجموعه IPهای مشاهده‌شده، زمان آخرین تغییر و تعداد تغییرات. فقط داده‌ای منتشر شود که برای افشای عمومی مناسب است.

### `countries.json`

فهرست کشورها با کد، تعداد کانفیگ، تعداد Fixed Verified، تعداد Rotating و زمان آخرین GeoIP lookup. کشور ناشناخته در `unknown_count` جمع می‌شود.

### `rankings.json`

رتبه‌بندی Fixed، Rotating، Fastest و Balanced. هر ردیف باید `rank`, `config_id`, `score`, `score_components` و زمان تازگی اندازه‌گیری را داشته باشد.

## ۵. قرارداد State

### `state/configs.json`

Registry جاری کانفیگ‌ها. کلید اصلی `config_id` است. وضعیت، URI، منبع کشف، پروتکل، زمان‌ها و آخرین تست در این فایل ذخیره می‌شود.

### `state/ip-history.json`

دفتر شواهد IP. هر مشاهده شامل `config_id`, `run_id`, `observed_at`, `ip`, `ip_family`, `observers`, `consensus`, `geo` و نتیجه است. رکورد قبلی نباید پاک شود، مگر طبق سیاست نگهداری و بعد از Snapshot تاریخچه.

### `state/metrics.json`

آخرین اندازه‌گیری‌ها و خلاصه معیارها. هر معیار باید واحد، زمان و روش اندازه‌گیری داشته باشد.

## ۶. قرارداد History

- `daily`: خلاصه تمام Runهای همان روز UTC و آمار روزانه.
- `weekly`: جمع‌بندی روزهای هفته ISO؛ نباید با جمع ساده مقادیر متوسط اشتباه شود.
- `monthly`: خلاصه ماه UTC.
- فایل‌های History بعد از انتشار موفق باید immutable تلقی شوند. اصلاح خطا باید با نسخه یا رویداد اصلاحی ثبت شود، نه حذف بی‌ردپا.

## ۷. سازگاری داده

قبل از تغییر نام یا ساختار فایل موجود، Migration لازم است. ابزار مهاجرت باید نسخه قدیم و جدید را تشخیص دهد، Backup بسازد، تعداد رکوردها را مقایسه کند و در صورت خطا از انتشار جلوگیری کند.

# ۰۳ — Collector و مدیریت منابع

## ۱. مسئولیت

Collector کانفیگ‌ها را از منابع پیکربندی‌شده دریافت می‌کند. این ماژول باید منبع، زمان دریافت، وضعیت HTTP و تعداد رکوردهای استخراج‌شده را ثبت کند. Collector نباید ورودی نامعتبر را بی‌صدا حذف کند؛ شمارش و علت حذف باید در گزارش Run ثبت شود.

## ۲. رجیستری منابع

هر منبع باید metadata داشته باشد:

- `source_id`: شناسه پایدار و یکتا.
- `url`: نشانی منبع.
- `format`: نوع ورودی، مانند raw URI list، Base64 subscription، JSON یا متن.
- `enabled`: فعال یا غیرفعال.
- `priority`: ترتیب پردازش، نه امتیاز کیفیت کانفیگ.
- `timeout_seconds`: سقف زمان دریافت.
- `max_bytes`: سقف اندازه پاسخ.
- `max_redirects`: حداکثر تغییر مسیر.
- `refresh_interval`: بازه مجاز دریافت.
- `trust_level`: فقط برای کنترل منبع و گزارش؛ جایگزین اعتبارسنجی کانفیگ نیست.

## ۳. دریافت امن

- فقط HTTP و HTTPS مجاز باشند؛ پروتکل‌های دیگر برای Source URL رد شوند.
- TLS certificate validation فعال باشد.
- Redirectها محدود و در هر گام دوباره بررسی شوند.
- IP مقصد پس از DNS resolution کنترل شود.
- دسترسی به loopback، private، link-local، multicast، reserved و metadata address مسدود شود.
- پاسخ، اندازه، زمان و تعداد Redirect محدود شود.
- فایل‌های فشرده فقط با سقف حجم بازشوند؛ Zip bomb باید رد شود.
- Headerهای محرمانه هرگز در لاگ ثبت نشوند.
- خطای یک منبع کل Pipeline را متوقف نکند؛ مگر آن‌که منبع حیاتی طبق تنظیمات مشخص شده باشد.

## ۴. Parser و فرمت ورودی

Parser باید فرمت را صریح تشخیص دهد یا از تنظیم منبع دریافت کند. فرمت‌های قابل پشتیبانی می‌توانند شامل URIهای `vless://`, `vmess://`, `trojan://`, `ss://` و Subscription Base64 باشند. Parser باید UTF-8 را اولویت دهد و در خطا، علت قابل گزارش تولید کند.

Parser نباید صرفاً به دلیل شباهت رشته، URI را معتبر اعلام کند. اعتبارسنجی نهایی با Validator انجام می‌شود.

## ۵. Normalization

Normalization باید کمینه و قابل تکرار باشد:

- حذف فاصله ابتدا و انتهای خط.
- حذف خط خالی و Comment طبق قواعد منبع.
- نرمال‌سازی حروف Scheme و Host در بخش‌های مجاز URI.
- حفظ پارامترهایی که معنای پروتکلی دارند.
- حذف Fragment فقط در صورتی که Fragment در قرارداد URI برای اتصال استفاده نشود.
- عدم بازنویسی دلخواه Query، رمزنگاری یا Percent-Encoding.

هر تغییر Normalization باید نسخه‌دار باشد تا `config_id` بدون برنامه مهاجرت عوض نشود.

## ۶. Deduplication و config_id

`config_id` باید از SHA-256 نمایش Canonical URI ساخته شود. الگوریتم Canonicalization باید نسخه داشته باشد. دو URI فقط زمانی تکراری هستند که پس از Canonicalization نسخه یکسان، کلید یکسان بسازند.

برای ردیابی چند منبع، یک کانفیگ می‌تواند چند `source_id` داشته باشد. Deduplication نباید منشأهای کشف را از بین ببرد.

## ۷. خروجی Collector

خروجی هر اجرا باید شامل موارد زیر باشد:

- تعداد منابع موفق، ناموفق و محدودشده.
- تعداد خطوط/رکوردهای ورودی.
- تعداد URIهای Parseشده.
- تعداد URIهای تکراری.
- تعداد URIهای ردشده و علت‌ها.
- فهرست شناسه‌های کانفیگ جدید و شناخته‌شده.
- زمان دریافت و شناسه منبع.

## ۸. معیار پذیرش

- Source timeout و پاسخ بزرگ کنترل می‌شوند.
- SSRF در DNS و Redirect رد می‌شود.
- ورودی Base64 خراب با خطای مشخص رد می‌شود.
- یک URI تکراری از چند منبع، یک `config_id` می‌سازد و چند منشأ را حفظ می‌کند.
- Parser با ورودی ناقص Crash نمی‌کند.

# ۰۴ — Validator

## ۱. هدف

Validator مشخص می‌کند کانفیگ از نظر ساختار، سیاست امنیتی و دسترسی اولیه قابل آزمایش است یا خیر. موفقیت Validator هیچ‌گاه به معنی Fixed یا حتی اتصال موفق Xray نیست.

## ۲. مراحل اعتبارسنجی

### Syntax Validation

- Scheme در فهرست مجاز باشد.
- Host، Port و اطلاعات احراز هویت مطابق پروتکل وجود داشته باشند.
- Port در محدوده معتبر باشد.
- Query و مقدارهای رمزنگاری‌شده Parse شوند.
- فیلدهای اجباری پروتکل وجود داشته باشند.
- مقدارهای ناشناخته یا ناسازگار طبق سیاست رد یا علامت‌گذاری شوند.

### Security Validation

- مقصد نباید loopback، private، link-local، multicast، reserved یا metadata endpoint باشد.
- اگر Host دامنه است، تمام A/AAAAهای resolve شده بررسی شوند.
- DNS rebinding باید در زمان اتصال نیز کنترل شود.
- مقصد Resolveشده باید با مقصدی که TCP Test به آن وصل می‌شود منطبق باشد.
- پورت‌های ممنوع یا پرخطر از Policy قابل تنظیم پیروی کنند.
- مقدارهای ورودی نباید به Shell یا Command Line تزریق شوند.
- کانفیگ نباید فایل یا مسیر دلخواه روی Runner بنویسد.

### TCP Preflight

- اتصال TCP به مقصد با Timeout کوتاه و محدود اجرا شود.
- تست فقط شاخص دسترسی TCP است؛ جایگزین تست TLS، پروتکل یا Xray نیست.
- خطاهای DNS، Refused، Timeout و Network Unreachable جدا ثبت شوند.

## ۳. وضعیت اعتبارسنجی

`VALID`, `INVALID_SYNTAX`, `BLOCKED_SECURITY_POLICY`, `TCP_UNREACHABLE`, `TCP_TIMEOUT`, `DNS_FAILURE`, `VALIDATION_ERROR`.

وضعیت Validation از وضعیت Intelligence جدا است. یک کانفیگ می‌تواند `VALID` باشد اما `UNSTABLE` یا `ROTATING` باشد.

## ۴. ثبت رویداد

برای هر کانفیگ، زمان، نسخه Validator، مرحله، نتیجه و کد علت ذخیره شود. متن کامل URI یا Credential در لاگ خطا چاپ نشود.

## ۵. معیار پذیرش

- ورودی خراب بدون Crash رد شود.
- IPv4 و IPv6 مقصد جداگانه ثبت شوند.
- DNS پاسخ خصوصی رد شود.
- Redirect یا DNS تغییرکرده باعث دورزدن کنترل نشود.
- TCP Timeout با عدم اعتبار Syntax اشتباه گرفته نشود.

# ۰۵ — Tester و Xray Core

## ۱. هدف

Tester عملکرد واقعی Tunnel را بررسی می‌کند. Xray Core باید نسخه Pin شده داشته باشد. دریافت Binary بدون بررسی Hash یا امضای معتبر مجاز نیست.

## ۲. چرخه تست

1. بررسی فایل Binary و نسخه Xray.
2. ساخت Config موقت از کانفیگ مورد آزمایش.
3. تخصیص پورت محلی آزاد و تصادفی.
4. اجرای Xray در Process ایزوله.
5. بررسی Startup و Log بدون افشای Credential.
6. ارسال Probe از داخل Tunnel.
7. دریافت IP خروجی از چند Observer.
8. اندازه‌گیری معیارهای کیفیت در صورت موفقیت.
9. خاتمه Process و پاک‌سازی فایل‌ها و پورت‌ها.
10. ثبت Test Result با `test_id` و `run_id`.

## ۳. ایزوله‌سازی

- Process برای هر کانفیگ باید محدودیت زمان داشته باشد.
- پورت محلی بین تست‌ها تداخل نداشته باشد.
- فایل موقت دارای Permission محدود باشد.
- در مسیرهای خطا نیز Process خاتمه یابد.
- تعداد تست موازی براساس CPU و RAM Runner محدود شود.
- Log حاوی UUID، Password، Private Key یا URL کامل منتشر نشود.
- کانفیگ نباید دسترسی Runner را به شبکه داخلی باز کند. سیاست Security Validation باید پیش از اجرا اعمال شود.

## ۴. Connectivity Test

نتیجه شامل `connected`, `failed`, `timeout`, `process_error` و علت مشخص است. Probe باید از داخل Proxy محلی عبور کند. تست مستقیم از Runner برای سنجش Tunnel قابل قبول نیست.

## ۵. IP Egress Test

Observerها باید endpointهای مستقل و قابل اعتماد باشند. هر پاسخ شامل IP parseشده، خانواده IP، زمان، Observer ID و نتیجه HTTP باشد. پاسخ غیر IP یا پاسخ غیرقابل اعتماد نباید به‌عنوان مشاهده پذیرفته شود.

قواعد:
- IPv4 و IPv6 جداگانه بررسی شوند.
- هر Observer از مسیر Tunnel درخواست شود.
- حداقل تعداد Observer موفق از تنظیمات خوانده شود.
- اگر Observerهای موفق IP متفاوت گزارش کنند، `consensus=false` و وضعیت IP `IP_UNVERIFIED` است.
- timeout یک Observer به‌تنهایی اختلاف IP نیست؛ اما ممکن است Quorum را ناکافی کند.

## ۶. Latency

Latency باید از داخل Tunnel اندازه‌گیری شود. تعریف دقیق Probe باید ثابت باشد: زمان درخواست تا پاسخ برای endpoint کنترل‌شده یا اتصال TCP به مقصد آزمایشی. مقدار باید بر حسب میلی‌ثانیه ثبت شود.

فیلدهای پیشنهادی:
- `latency_ms` برای مقدار اصلی.
- `latency_samples_ms` برای نمونه‌ها.
- `latency_p50_ms`, `latency_p95_ms` برای توزیع.
- `measurement_method` و `measured_at`.

ICMP Ping ممکن است توسط سرور مسدود باشد؛ بنابراین نباید تنها معیار Latency باشد.

## ۷. Throughput

Throughput فقط با انتقال داده به endpoint کنترل‌شده و با سقف مشخص حجم/زمان اندازه‌گیری شود. برای جلوگیری از مصرف منابع، هر تست باید `max_bytes` و `timeout_seconds` داشته باشد. مقدار بر حسب bit/s یا byte/s همراه با واحد ذخیره شود؛ واحدها در یک API نباید مخلوط شوند.

اگر تست اجرا نشده است، مقدار `null` باشد. عدد ساختگی، مقدار پیش‌فرض یا تخمین نباید منتشر شود.

## ۸. Uptime و پایداری اتصال

Runner عادی GitHub اجرای دائمی ندارد. بنابراین uptime باید از نسبت موفقیت Runهای مستقل در یک بازه تعریف‌شده محاسبه شود، نه از ادعای مانیتورینگ پیوسته.

`uptime_ratio = successful_scheduled_checks / eligible_scheduled_checks`.

Runهای دستی، Runهای لغوشده و Runهای فاقد تست نباید بدون سیاست مشخص در مخرج قرار گیرند.

## ۹. مدل نتیجه تست

هر Test Result باید شامل `test_id`, `run_id`, `config_id`, `started_at`, `finished_at`, `xray_version`, `connectivity`, `ip_observation`, `metrics` و `error_code` باشد.

## ۱۰. معیار پذیرش

- Xray با نسخه ثابت اجرا می‌شود.
- Process بعد از موفقیت و شکست پاک‌سازی می‌شود.
- درخواست IP از داخل Tunnel خارج می‌شود.
- دو Observer با IP متفاوت باعث عدم اجماع می‌شوند.
- شکست IPv4، تست IPv6 را بی‌دلیل مخفی نمی‌کند و برعکس.
- Throughput فقط با اندازه‌گیری واقعی ثبت می‌شود.

# ۰۶ — موتور هوشمندی IP و طبقه‌بندی

## ۱. اولویت تصمیم

هدف این موتور تعیین وضعیت IP خروجی هر کانفیگ است. یک مشاهده موفق یا چند درخواست در یک Run برای اثبات IP ثابت کافی نیست. شواهد باید از Runهای مستقل و در بازه زمانی معنادار جمع شوند.

## ۲. مفاهیم

- **Observation:** یک مشاهده IP برای یک کانفیگ در یک Run.
- **Observer:** سرویس مستقلی که IP درخواست را گزارش می‌کند.
- **Consensus:** توافق Observerهای موفق در یک Observation.
- **Run مستقل:** اجرای مجزای Pipeline در زمان جداگانه. تکرار درخواست در یک Process، Run مستقل محسوب نمی‌شود.
- **Egress IP:** IP عمومی‌ای که مقصد اینترنت از طریق تونل می‌بیند.
- **IP Family:** مقدار IPv4 یا IPv6.

## ۳. وضعیت‌های کانفیگ

| وضعیت | معنی | مجاز برای `fixed-verified.txt` |
|---|---|---|
| `DISCOVERED` | تازه دریافت شده | خیر |
| `VALIDATED` | Syntax و Security موفق | خیر |
| `TESTED` | حداقل یک تست Xray موفق | خیر |
| `FIXED_CANDIDATE` | چند مشاهده همسان، اما شواهد هنوز به حد تأیید نرسیده | خیر |
| `FIXED_VERIFIED` | IP در تعداد Run و بازه زمانی مقرر ثابت مانده | بله |
| `ROTATING` | تغییر IP در Runهای مستقل تأیید شده | خیر |
| `UNSTABLE` | اتصال یا مشاهده IP قابل اتکا نیست | خیر |
| `IP_UNVERIFIED` | Quorum یا اجماع Observerها کافی نیست | خیر |
| `QUARANTINED` | ریسک امنیتی یا رفتار غیرعادی | خیر |
| `EXPIRED` | مدت طولانی بدون تست معتبر | خیر |
| `INVALID` | ورودی دیگر معتبر نیست | خیر |

## ۴. منطق اجماع Observerها

برای هر خانواده IP، Observerها جدا فراخوانی شوند. یک Observation زمانی معتبر است که حداقل تعداد تنظیم‌شده Observer پاسخ معتبر بدهند. تمام پاسخ‌های معتبر باید یک IP یکسان گزارش کنند. اگر دو IP متفاوت گزارش شود، Observation فاقد اجماع است.

این سیاست محافظه‌کارانه است. در صورت نیاز به رأی اکثریت، باید حداقل Quorum، نسبت توافق، مدیریت Observer خراب و ریسک رأی اشتباه به‌صورت ADR جدا تصویب شود.

## ۵. سیاست پیشنهادی تشخیص Fixed

مقادیر زیر **پیش‌فرض پیشنهادی** هستند و قبل از استقرار باید در فایل تنظیمات تأیید شوند:

- `FIXED_CANDIDATE`: حداقل ۳ Run مستقل موفق، IP یکسان، حداقل ۲ Observer معتبر در هر Run و گستره زمانی حداقل ۲۴ ساعت.
- `FIXED_VERIFIED`: حداقل ۶ Run مستقل موفق، IP یکسان، حداقل ۲ Observer معتبر در هر Run و گستره زمانی حداقل ۷۲ ساعت.
- تمام Observationهای معتبر در پنجره تأیید باید همان IP را نشان دهند.
- هر اختلاف IP تأییدشده، شواهد Fixed فعلی را باطل می‌کند و طبقه‌بندی را دوباره محاسبه می‌کند.

تعداد درخواست‌ها در یک Run نباید جای تعداد Runهای مستقل را بگیرد. اجرای چندباره فوری برای عبور از آستانه مجاز نیست.

## ۶. سیاست پیشنهادی تشخیص Rotating

یک کانفیگ زمانی `ROTATING` می‌شود که در حداقل دو Run مستقل، حداقل دو IP خروجی متفاوت با Observation معتبر و اجماع Observerها ثبت شود. تعداد تغییرات، زمان تغییر و مجموعه IPها در History نگهداری می‌شود.

اگر اختلاف فقط بین Observerهای یک Run باشد، نتیجه `IP_UNVERIFIED` است، نه `ROTATING`.

## ۷. IPv4 و IPv6

شواهد هر خانواده جدا نگهداری شود. یک کانفیگ ممکن است IPv4 ثابت و IPv6 چرخشی داشته باشد. وضعیت کلی باید این تفاوت را نمایش دهد. برای اشتراک Fixed با شرط خانواده مشخص، فیلتر خانواده IP باید صریح باشد.

پیشنهاد مدل:
- `ip_status.ipv4`
- `ip_status.ipv6`
- `ip_status.overall`

`overall=FIXED_VERIFIED` تنها زمانی مجاز است که سیاست خانواده‌های موردنیاز برقرار باشد. اگر فقط IPv4 اندازه‌گیری شده، ادعای Fixed برای IPv6 ممنوع است.

## ۸. وضعیت و انتقال‌ها

انتقال‌ها باید با رویداد ثبت شوند. نمونه مسیر:

`DISCOVERED → VALIDATED → TESTED → FIXED_CANDIDATE → FIXED_VERIFIED`

مسیر دیگر:

`TESTED → ROTATING`

خطای موقت اتصال می‌تواند وضعیت `UNSTABLE` ایجاد کند. اختلاف Observerها می‌تواند `IP_UNVERIFIED` ایجاد کند. خطر امنیتی می‌تواند به `QUARANTINED` منتقل کند.

بازگشت از `ROTATING` به Fixed باید با پنجره شواهد تازه انجام شود؛ تاریخچه IP قبلی حذف نمی‌شود.

## ۹. انقضای شواهد

شواهد قدیمی ممکن است دیگر نماینده وضعیت فعلی نباشند. `fixed_evidence_max_age` باید در تنظیمات تعریف شود. اگر شواهد قدیمی شوند، کانفیگ از `FIXED_VERIFIED` خارج یا به حالت نیازمند تأیید مجدد منتقل می‌شود. نباید وضعیت Verified برای همیشه باقی بماند.

## ۱۰. توضیح‌پذیری

هر تصمیم باید `classification_reason_codes` داشته باشد؛ مانند:
- `INSUFFICIENT_RUNS`
- `INSUFFICIENT_TIME_SPAN`
- `OBSERVER_DISAGREEMENT`
- `IP_CHANGED_ACROSS_RUNS`
- `IP_CONSISTENT_THRESHOLD_MET`
- `EVIDENCE_EXPIRED`

## ۱۱. معیار پذیرش

- چند تست در یک Run یک Run مستقل حساب نمی‌شوند.
- Observerهای متعارض، Fixed تولید نمی‌کنند.
- IP متفاوت در دو Run معتبر، Fixed را باطل می‌کند.
- IPv4 و IPv6 با هم مخلوط نمی‌شوند.
- شواهد قدیمی از وضعیت Verified خارج می‌شوند.
- هر تغییر طبقه‌بندی، دلیل و زمان دارد.

# ۰۷ — موتور رتبه‌بندی

## ۱. اصول

رتبه‌بندی باید از اندازه‌گیری واقعی استفاده کند. هیچ معیار ناموجودی نباید به عدد فرضی تبدیل شود. امتیاز Fixed و Rotating جدا محاسبه شود، زیرا معیار مناسب یک IP ثابت با یک IP چرخشی یکسان نیست.

## ۲. معیارها

| معیار | واحد | تعریف |
|---|---|---|
| Latency | ms | زمان پاسخ از داخل Tunnel |
| Throughput | bit/s یا byte/s | نرخ انتقال داده با روش ثبت‌شده |
| Connection success | ratio | نسبت تست‌های اتصال موفق |
| Uptime estimate | ratio | نسبت Probeهای زمان‌بندی‌شده موفق |
| IP stability | score/ratio | میزان ثبات IP در بازه ارزیابی |
| Evidence freshness | seconds | سن آخرین شواهد معتبر |
| Error rate | ratio | نسبت خطاهای واجد شرایط |

## ۳. نرمال‌سازی

معیارها مقیاس متفاوت دارند. قبل از جمع وزن‌دار باید به بازه مشترک تبدیل شوند. تبدیل باید با تابع و پارامتر ثابت نسخه‌دار انجام شود. برای latency کمتر بهتر است؛ برای throughput و success بیشتر بهتر است.

داده قدیمی باید حذف یا با جریمه تازگی مدیریت شود. داده `null` نباید صفر تلقی شود.

## ۴. امتیازهای جداگانه

### Fixed Score

برای Fixed، تأیید IP و پایداری در اولویت هستند. یک مدل پیشنهادی:

`fixed_score = w_ip * ip_stability + w_success * connection_success + w_latency * latency_score + w_uptime * uptime_estimate + w_fresh * freshness_score`

وزن‌ها باید جمعاً ۱ باشند. شرط ورود به `fixed-top50.txt` علاوه بر امتیاز، وضعیت `FIXED_VERIFIED` است.

### Rotating Score

برای Rotating، کارایی اتصال و تازگی تست اهمیت دارد. امتیاز این گروه نباید به‌عنوان Fixed Score نمایش داده شود.

### Fastest

مرتب‌سازی بر اساس Latency معتبر و تازه. در صورت برابر بودن، معیار ثانویه باید deterministic باشد؛ برای نمونه `config_id`.

### Balanced

امتیاز چندمعیاره با وزن‌های قابل تنظیم. API باید اجزای امتیاز را ارائه کند تا دلیل رتبه قابل بررسی باشد.

## ۵. سیاست داده ناقص

دو روش ممکن است:

1. حذف کانفیگ از رتبه‌بندی زمانی که معیار حیاتی موجود نیست.
2. محاسبه امتیاز با وزن‌های باقیمانده و ثبت `score_coverage`.

روش دوم نباید امتیاز کانفیگ کم‌داده را با کانفیگ کامل هم‌سطح کند. پیشنهاد این است که `score_coverage` حداقل لازم داشته باشد و API آن را نمایش دهد.

## ۶. تازگی معیارها

هر معیار `measured_at` دارد. معیار قدیمی‌تر از `metrics.max_age` وارد Fastest و Balanced نشود، مگر سیاست جداگانه تعریف شده باشد.

## ۷. Tie-break و پایداری خروجی

برای یک ورودی یکسان، خروجی رتبه‌بندی باید یکسان باشد. ترتیب ثانویه باید قطعی باشد. مقایسه رشته‌ای یا ترتیب Hash Map نباید خروجی تصادفی ایجاد کند.

## ۸. تنظیمات وزن

وزن‌های نهایی هنوز تصمیم محصول هستند. آن‌ها باید در تنظیمات نسخه‌دار ذخیره شوند. تغییر وزن باید در `ranking_policy_version` و API ثبت شود تا مقایسه تاریخچه گمراه‌کننده نشود.

# ۰۸ — سیستم Distribution و Subscription

## ۱. هدف

این لایه نتایج معتبر را به لینک‌های قابل استفاده برای کلاینت‌های V2Ray تبدیل می‌کند. این لایه نباید کانفیگ را تست یا طبقه‌بندی کند؛ فقط از وضعیت و معیارهای تأییدشده استفاده می‌کند.

## ۲. خروجی‌ها

- اشتراک عمومی: `sub/main.txt`
- اشتراک Fixed: `sub/fixed.txt`
- اشتراک Fixed تأییدشده: `sub/fixed-verified.txt`
- برترین Fixed: `sub/fixed-top50.txt`
- اشتراک Rotating: `sub/rotating.txt`
- برترین Rotating: `sub/rotating-top50.txt`
- سریع‌ترین: `sub/fastest.txt`
- متوازن: `sub/balanced.txt`
- دسته‌بندی کشور: `sub/country/<CC>.txt`
- دسته‌بندی پروتکل: `sub/protocol/<protocol>.txt`

## ۳. ترتیب URIها

- `main`: بر اساس سیاست رتبه‌بندی عمومی.
- `fixed`: ابتدا Verified و سپس Candidate، با وضعیت Candidate قابل تشخیص در API.
- `fixed-verified`: فقط Verified.
- `fixed-top50`: Verifiedهای برتر.
- `rotating`: بر اساس Rotating Score.
- `fastest`: Latency از کم به زیاد.
- `balanced`: Balanced Score از زیاد به کم.

## ۴. فرمت خروجی

فرمت پیش‌فرض باید Base64 از خطوط URI باشد؛ Encoding باید در تنظیمات مشخص شود و در تمام اشتراک‌ها یکسان باشد. هیچ سربرگ، Comment یا پیام وضعیت نباید داخل Subscription قرار گیرد. اطلاعات توضیحی در API و README منتشر شود.

## ۵. جلوگیری از افشای ناخواسته

- فقط منابعی که برای انتشار عمومی مجاز هستند وارد اشتراک شوند.
- فایل اشتراک عمومی است و هر URI آن قابل استخراج است.
- Credentialها نباید در لاگ یا خطای Workflow ثبت شوند.
- خروجی عمومی نباید شامل Source Token، API Key یا Header محرمانه باشد.

## ۶. کنترل کیفیت پیش از انتشار

- هر URI خروجی Parse می‌شود.
- تعداد خطوط و تعداد کانفیگ‌های منتخب با آمار API مقایسه می‌شود.
- Duplicate URI در یک فایل حذف می‌شود.
- ترتیب فایل باید قطعی باشد.
- `fixed-verified.txt` فقط شامل `FIXED_VERIFIED` باشد.
- `country` با GeoIP خروجی منطبق باشد.
- فایل‌های خالی به‌صورت صفر بایت تولید شوند.

# ۰۹ — API استاتیک نسخه ۱

## ۱. معماری API

API نسخه اول Backend زنده ندارد. هر Endpoint یک فایل JSON است که Pipeline تولید می‌کند. فایل‌ها در شاخه `data` قرار می‌گیرند و می‌توان آن‌ها را از GitHub Raw یا GitHub Pages سرو کرد.

ریشه پیشنهادی:

`https://raw.githubusercontent.com/TOW-AI/v2ray-pool/data/api/v1/`

نمونه Endpointها:
- `stats.json`
- `configs.json`
- `fixed.json`
- `rotating.json`
- `countries.json`
- `rankings.json`

## ۲. قرارداد پاسخ

همه Endpointها باید `schema_version`, `generated_at`, `run_id`, `source_commit`, `data_commit`, `data_age_seconds` داشته باشند. Client باید نسخه Schema را بررسی کند و در فیلدهای ناشناخته Fail نکند.

## ۳. `stats.json`

موارد پیشنهادی:
- `totals.discovered`
- `totals.validated`
- `totals.tested`
- `totals.publishable`
- `statuses` برای تمام وضعیت‌ها
- `protocols` تعداد هر پروتکل
- `countries` تعداد کشورها
- `tests.successful`, `tests.failed`, `tests.skipped`
- `freshness.last_successful_run_at`
- `freshness.oldest_published_measurement_at`

## ۴. `configs.json`

هر رکورد عمومی:
- `config_id`
- `protocol`
- `status`
- `verification_level`
- `ip_status` با IPv4/IPv6/overall
- `egress_ip` و `ip_family` در صورت تأیید
- `country_code` و `country_name`
- `last_test_at`
- `metrics` شامل مقدار، واحد و زمان
- `scores` و `score_coverage`
- `uri` فقط برای کانفیگ مجاز به انتشار عمومی

## ۵. `fixed.json` و `rotating.json`

این دو فایل باید مجموعه‌ای از همان مدل Config باشند، اما فیلتر و داده اختصاصی گروه را هم داشته باشند. `fixed.json` باید تعداد Evidence، بازه زمانی اثبات و زمان آخرین مشاهده را نشان دهد. `rotating.json` باید تاریخچه خلاصه IPهای مختلف و تعداد تغییرهای تأییدشده را نشان دهد.

## ۶. `countries.json`

کشورها با کد ISO مرتب شوند. برای هر کشور تعداد کل، Fixed Verified، Rotating و زمان آخرین GeoIP update ارائه شود. تعدادهای کشور نامشخص در `unknown` نگهداری شود.

## ۷. `rankings.json`

چهار فهرست مستقل:
- `fixed`
- `rotating`
- `fastest`
- `balanced`

هر عضو باید `rank`, `config_id`, `score`, `score_components`, `score_coverage`, `measured_at` داشته باشد. Fastest می‌تواند بر اساس latency خام مرتب شود؛ در آن صورت مقدار و واحد latency نیز لازم است.

## ۸. صفحه‌بندی

در نسخه فایل استاتیک، صفحه‌بندی سروری وجود ندارد. اگر تعداد رکوردها بزرگ شد، نسخه بعدی می‌تواند فایل‌ها را بر اساس حروف شناسه یا کشور Split کند. تا آن زمان، اندازه فایل باید در Workflow کنترل شود.

## ۹. Cache و به‌روزرسانی

`generated_at` و `data_age_seconds` برای تشخیص تازگی استفاده می‌شوند. مصرف‌کننده نباید فرض کند فایل JSON لحظه‌ای است. Cache-Control در GitHub Raw در اختیار کامل موتور نیست؛ در GitHub Pages می‌توان Headerهای مناسب را پیکربندی کرد.

## ۱۰. سازگاری نسخه

تغییر ناسازگار در ساختار باید به `/v2/` منتقل شود. تغییرات افزایشی می‌توانند در v1 انجام شوند، اما باید در Release Notes ثبت شوند. Schema JSON در `schemas/` منبع قرارداد است.

# ۱۰ — State و History

## ۱. تفاوت State و History

**State** آخرین تصویر قابل استفاده از سیستم است. **History** شواهد و رخدادهای گذشته را نگه می‌دارد. State قابل بازسازی از History است، اما History نباید از State فعلی حدس زده شود.

## ۲. `state/configs.json`

Registry کانفیگ‌ها و وضعیت جاری آن‌ها. کلید رکورد `config_id` است. فیلدهای مهم:
- Canonical URI و نسخه Canonicalizer.
- Protocol و Source IDs.
- وضعیت Validation و Classification.
- زمان کشف، آخرین مشاهده، آخرین تست و انقضا.
- آخرین IP تأییدشده به تفکیک IPv4/IPv6.
- شمار Runهای موفق و دلایل وضعیت.

## ۳. `state/ip-history.json`

این فایل دفتر شواهد IP است. رکوردهای آن append-only هستند. هر Observation شامل:
- `observation_id`
- `config_id`
- `run_id`
- `observed_at`
- `ip_family`
- `ip`
- `observers[]`
- `consensus`
- `geo`
- `result_code`

Observation ناموفق هم می‌تواند ثبت شود، اما باید `ip=null` و علت شکست داشته باشد.

## ۴. `state/metrics.json`

آخرین معیارهای معتبر به تفکیک کانفیگ و معیار. هر معیار دارای `value`, `unit`, `measured_at`, `method`, `test_id` و `validity` است. مقادیر قدیمی ممکن است در History بمانند اما برای رتبه‌بندی جاری قابل استفاده نباشند.

## ۵. فایل‌های History

### Daily

خلاصه Runهای روز UTC. شامل تعداد دریافت، Validation، اتصال، وضعیت‌های IP، رتبه‌بندی و خطاها.

### Weekly

جمع‌بندی هفته ISO. برای میانگین Latency از داده نمونه یا روش تجمیع معتبر استفاده شود؛ میانگین‌گیری از میانگین‌های روزانه بدون وزن نمونه‌ها ممکن است غلط باشد.

### Monthly

تجمیع ماهانه و روند تغییر وضعیت‌ها. باید تعداد داده‌های پایه برای هر میانگین مشخص باشد.

## ۶. نوشتن امن

- فایل جدید ابتدا در فایل موقت نوشته شود.
- JSON Parse و Schema Validate شود.
- فایل با Rename اتمیک جایگزین شود.
- قبل از Commit، تعداد Config IDها و Observationها بررسی شود.
- فقط بعد از Snapshot موفق، سیاست Retention می‌تواند داده قدیمی را Archive کند.

## ۷. بازیابی

در صورت خراب شدن State، آخرین Backup معتبر یا History برای بازسازی استفاده شود. بازسازی باید تعداد رکورد ورودی، خروجی، رکوردهای ردشده و علت آن‌ها را گزارش کند. اگر رکوردی قابل بازیابی نیست، سیستم نباید خاموش و بی‌صدا آن را حذف کند.

## ۸. مهاجرت از State قدیمی

- فایل قدیمی را فقط خواندنی نگه دار.
- Backup با زمان UTC بساز.
- فیلدهای قدیمی را به مدل جدید Map کن.
- شناسه‌ها را تا حد امکان حفظ کن.
- شواهد IP را از داده واقعی مهاجرت بده؛ تاریخچه‌ای که وجود ندارد نساز.
- تعداد قبل و بعد را گزارش کن.
- در صورت افت تعداد غیرمنتظره، انتشار را متوقف کن.

## ۹. Retention

مقادیر Retention باید قابل تنظیم باشند. قبل از حذف History، Export آرشیو و کنترل Integrity لازم است. `state/ip-history.json` می‌تواند با بزرگ شدن، به فایل‌های partition شده تبدیل شود؛ این تغییر نیازمند Migration و Schema version جدید است.

- خطای Parse JSON نباید به نمایش اعداد ساختگی منجر شود.

## ۶. امنیت فرانت‌اند

# ۱۲ — GitHub Actions، شاخه‌ها و انتشار

## ۱. مدل Branch

- `main`: کد موتور، تنظیمات و مستندات.
- `data`: خروجی‌های عمومی، State و History.
- `feature/intelligence-engine-v2`: شاخه توسعه مستقل.

توسعه نباید مستقیماً روی `main` یا `data` انجام شود. انتشار داده فقط از Workflow معتبر انجام می‌شود.

## ۲. Workflowهای پیشنهادی

- `update.yml`: اجرای کامل Collector تا Publish.
- `benchmark.yml`: تست و بنچمارک مستقل یا تکمیلی.
- `history.yml`: تجمیع روزانه/هفتگی/ماهانه در صورت جداسازی نیاز.
- `maintenance.yml`: پاک‌سازی فایل موقت، بررسی سلامت و Retention.
- `validate.yml`: Lint، Unit Test، Schema Validation و بررسی مستندات در Pull Request.

Workflowها می‌توانند در نسخه اول ادغام شوند، اما مسئولیت‌های منطقی باید مستقل بمانند.

## ۳. اجرای Pipeline

Triggerها:
- `schedule` برای اجرای زمان‌بندی‌شده.
- `workflow_dispatch` برای اجرای دستی.
- `workflow_call` در صورت نیاز به فراخوانی از Workflow دیگر.

اجرای دستی باید ورودی محدود و اعتبارسنجی‌شده داشته باشد؛ برای نمونه Full Run یا Test subset. ورودی کاربر نباید به Shell command متصل شود.

## ۴. Permissions

حداقل Permission لازم:
- `contents: read` برای دریافت کد.
- `contents: write` فقط برای مرحله انتشار شاخه `data`.

Permission نوشتن باید تا حد امکان فقط در Job مربوط به Publish فعال باشد. Token نباید در Log چاپ شود.

## ۵. دریافت شاخه data

Job انتشار باید شاخه `data` را جداگانه دریافت کند. خروجی جدید در Working Tree همان شاخه قرار می‌گیرد. ایجاد Git Repository جدید در پوشه خروجی و Push کردن تاریخچه مستقل، روش مجاز نیست.

## ۶. حفظ History و Push

- آخرین شاخه `data` را پیش از Commit دریافت کن.
- فایل‌های جدید را با داده قبلی ادغام کن.
- History قبلی را حفظ کن.
- هیچ Push اجباری انجام نده.
- اگر شاخه در فاصله اجرا تغییر کرد، Rebase یا Fetch/Merge امن انجام بده و خروجی را دوباره اعتبارسنجی کن.
- در تعارض State، انتشار را متوقف کن؛ آخرین داده را بی‌صدا بازنویسی نکن.

## ۷. Concurrency

برای جلوگیری از دو انتشار هم‌زمان، گروه Concurrency ثابت برای Pipeline داده تعریف شود. سیاست لغو اجرای قبلی باید متناسب با طول تست انتخاب شود. اگر اجرای قبلی حاوی داده جدید است، لغو آن نباید باعث از دست رفتن State شود.

## ۸. Publish اتمیک

انتشار فقط زمانی انجام شود که:
- تمام JSONها Parse شوند.
- Schemaها معتبر باشند.
- فایل‌های Subscription Decode شوند.
- آمار API با فایل‌ها سازگار باشد.
- `fixed-verified.txt` فقط Fixed Verified داشته باشد.
- هیچ فایل حساس یا Secret وارد Diff نشده باشد.
- History و State سازگار باشند.

سپس Commit با پیام شامل زمان و Run ID ساخته و Push شود.

## ۹. GitHub Pages و API

داشبورد می‌تواند از GitHub Pages منتشر شود و JSONها را از مسیر ثابت بخواند. Raw URL برای اشتراک و API ساده است، اما Cache و دسترس‌پذیری آن باید در نظر گرفته شود.

## ۱۰. محدودیت Runner جغرافیایی

GitHub-hosted Runner عادی تضمین نمی‌کند که از کشور انتخاب‌شده اجرا شود. بنابراین:
- Global Collection یعنی منابع می‌توانند جهانی باشند.
- Global GeoIP یعنی IP خروجی کانفیگ‌ها به کشور نگاشت می‌شود.
- Global Testing فقط با Runnerهای منطقه‌ای یا سرویس تست منطقه‌ای قابل ادعا است.

## ۱۱. خطاهای انتشار

در صورت Fail شدن Publish، خروجی جدید نباید بخشی در شاخه `data` باقی بگذارد. Artifact تشخیصی می‌تواند برای مدت محدود ذخیره شود، اما نباید شامل URI خصوصی یا Token باشد.

# ۱۳ — مدل تهدید و امنیت

## ۱. دارایی‌ها

- GitHub Token و Secretهای Workflow.
- URIها و Credentialهای اتصال.
- Xray Binary و Artifactها.
- State و History.
- Runner و شبکه داخلی آن.
- اعتبار و دسترس‌پذیری API و داشبورد.

## ۲. تهدیدها

- SSRF از طریق Source URL یا URI مقصد.
- DNS rebinding و Redirect به IP داخلی.
- اجرای کانفیگ مخرب در محیط Runner.
- تزریق Command یا Path.
- افشای Secret در Log یا Artifact.
- جایگزینی Xray Binary با فایل مخرب.
- خراب‌کردن State یا حذف History.
- Push اجباری یا Race Condition.
- ورودی حجیم، Zip Bomb و DoS.
- XSS در داشبورد با داده کنترل‌شده توسط منبع.

## ۳. کنترل‌های الزامی

### Network Egress

- Block کردن مقصدهای خصوصی، loopback، link-local، multicast، reserved و metadata.
- بررسی DNS در زمان Resolve و قبل از اتصال.
- محدودیت Redirect و بررسی هر مقصد جدید.
- Timeout و محدودیت اندازه برای همه درخواست‌ها.

### Xray

- Version Pinning.
- بررسی SHA-256 یا امضای معتبر.
- اجرای با کمترین Permission.
- محدودیت زمان، حافظه، تعداد Process و پورت.
- عدم استفاده از Shell برای ساخت Command.
- پاک‌سازی Process در همه مسیرهای خروج.

### GitHub

- Least Privilege برای Token.
- Secretها فقط در GitHub Secrets.
- عدم چاپ Environment و Header.
- محدود کردن Write Permission به Job انتشار.
- عدم استفاده از `pull_request_target` برای اجرای کد غیرقابل اعتماد با Secret.
- عدم Push با `--force`.

### Public Data

- شاخه `data` عمومی فرض شود.
- فقط کانفیگ مجاز به انتشار در اشتراک قرار گیرد.
- منبع دارای Token یا URL امضاشده نباید در فایل عمومی ثبت شود.
- URIهای عمومی همچنان Credential اتصال دارند و قابل استفاده توسط دیگران هستند.

### Dashboard

- Escape همه داده‌های خارجی.
- منع Inline HTML از داده Source.
- منع چاپ URI در Console.
- استفاده از HTTPS.

## ۴. مدیریت Credential

Credential منبع و Credential اتصال دو دارایی متفاوت هستند. Source Token نباید در State یا API ذخیره شود. Credential اتصال در URI اشتراک عمومی ذاتاً منتشر می‌شود؛ بنابراین هیچ کانفیگ خصوصی نباید وارد خروجی عمومی شود.

## ۵. رخداد امنیتی

اگر Source مخرب، خروجی غیرعادی یا نشت Secret تشخیص داده شد:
1. Source را غیرفعال کن.
2. انتشار را متوقف کن.
3. Token افشاشده را Revoke/Rotate کن.
4. Run و Commit آلوده را شناسایی کن.
5. داده عمومی آلوده را با Commit اصلاحی حذف کن.
6. History رخداد و اقدام اصلاحی را ثبت کن.

## ۶. معیار پذیرش امنیتی

- تست SSRF برای IPv4 و IPv6.
- تست DNS rebinding و Redirect.
- بررسی عدم وجود Secret در Log و Artifact.
- بررسی Hash باینری Xray.
- تست پاک‌سازی Process بعد از Timeout.
- اسکن خروجی عمومی برای Token و الگوهای Secret.

# ۱۵ — راهنمای عملیات و نگهداری

## ۱. چرخه معمول

1. بررسی وضعیت آخرین Workflow.
2. بررسی تعداد Sourceهای موفق و ناموفق.
3. بررسی تعداد کانفیگ‌های جدید، معتبر و تست‌شده.
4. بررسی IP Unverified و Observer disagreement.
5. بررسی تغییر غیرعادی در Fixed Verified.
6. بررسی حجم JSON، History و Subscription.
7. بررسی Commit نهایی شاخه `data`.

## ۲. Run ناموفق

اگر Pipeline پیش از Publish شکست خورد، شاخه `data` باید بدون تغییر باقی بماند. ابتدا Stage شکست‌خورده را مشخص کن. پس از رفع علت، Run جدید اجرا کن. خروجی ناقص را دستی در شاخه `data` قرار نده.

## ۳. افت ناگهانی تعداد Fixed Verified

این رخداد ممکن است از تغییر واقعی IP، منقضی‌شدن شواهد، خطای Observer یا تغییر Policy ناشی شود. قبل از برگرداندن وضعیت، Observationها و Run IDها بررسی شوند. وضعیت Verified نباید فقط برای حفظ تعداد قبلی بازگردانده شود.

## ۴. اختلاف Observerها

- زمان و پاسخ هر Observer را بررسی کن.
- سلامت خود Observer را مستقل بررسی کن.
- اگر Quorum کافی نیست، IP Unverified بماند.
- رأی دلخواه یا IP قبلی را به‌جای نتیجه جدید قرار نده.

## ۵. افزایش حجم State

- تعداد Observationها و حجم فایل را پایش کن.
- قبل از Partitioning، Migration و Backup طراحی کن.
- فایل History را بی‌ردپا حذف نکن.
- ساختار جدید باید با نسخه Schema ثبت شود.

## ۶. انتشار ناموفق به شاخه data

علت‌های معمول: Permission، Branch protection، Non-fast-forward، Conflict یا Concurrency. ابتدا آخرین Commit شاخه `data` دریافت شود. هیچ‌گاه برای حل سریع مشکل از Force Push استفاده نکن.

## ۷. هشدارهای سامانه

هشدارهای حداقل:
- هیچ Run موفقی در بازه مورد انتظار نیست.
- تعداد Fixed Verified به‌شدت تغییر کرده است.
- Observerها اختلاف غیرعادی دارند.
- Xray Binary Hash نامعتبر است.
- خروجی API با Subscription ناسازگار است.
- داده قدیمی‌تر از حداکثر عمر تعیین‌شده است.
- حجم State از حد عملیاتی عبور کرده است.

## ۸. Backup و Recovery

Backup باید از State و History شاخه data گرفته شود. بازیابی باید ابتدا در Branch موقت انجام شود. پس از Schema Validation و شمارش رکوردها، Pull Request یا انتشار کنترل‌شده انجام شود.

# ۱۷ — تصمیم‌های معماری و واژه‌نامه

## ۱. تصمیم‌های قطعی پروژه

| موضوع | تصمیم |
|---|---|
| زیرساخت | GitHub Actions؛ بدون VPS |
| سیاست IP | جداسازی Fixed و Rotating |
| توزیع | لینک اشتراک GitHub + API + داشبورد |
| محدوده جمع‌آوری | جهانی |
| اولویت اصلی | IP خروجی ثابت |
| شاخه توسعه | `feature/intelligence-engine-v2` |
| شاخه انتشار داده | `data` |
| شاخه کد پایدار | `main` |

## ۲. محدودیت پذیرفته‌شده

Global Collection به معنی Global Testing نیست. Runner عادی GitHub محل خروجی از کشور مشخص را تضمین نمی‌کند. برای تست منطقه‌ای واقعی باید زیرساخت منطقه‌ای جداگانه تصویب شود.

## ۳. تصمیم‌های باز که باید قبل از Production نهایی شوند

1. آستانه دقیق Fixed Candidate و Fixed Verified.
2. عمر مجاز شواهد Fixed و سیاست Reverification.
3. تعداد و فهرست Observerهای IP.
4. سیاست اجماع Observerها.
5. فرمت سازگار فایل‌های Subscription فعلی (`base64` یا `plain`).
6. وزن‌های Fixed، Rotating و Balanced.
7. حداکثر عمر معیارهای Performance.
8. سیاست ورود Rotating به `main.txt`.
9. Retention و اندازه مجاز `ip-history.json`.
10. دامنه انتشار URI در JSON API.

## ۴. واژه‌نامه

| اصطلاح | تعریف |
|---|---|
| Config | یک URI یا تعریف اتصال V2Ray |
| `config_id` | شناسه پایدار حاصل از Canonical URI |
| Run | یک اجرای مستقل Pipeline |
| Test | یک آزمون مشخص برای یک کانفیگ |
| Egress IP | IP عمومی قابل مشاهده از مقصد اینترنت |
| Observer | سرویس گزارش‌دهنده IP خروجی |
| Consensus | توافق Observerهای معتبر |
| Fixed Candidate | نامزد IP ثابت با شواهد اولیه |
| Fixed Verified | کانفیگ با شواهد کافی در چند Run و بازه مقرر |
| Rotating | کانفیگی با چند IP خروجی تأییدشده در Runهای جدا |
| IP Unverified | IP خروجی به علت فقدان Quorum یا اختلاف Observerها قابل تأیید نیست |
| GeoIP | نگاشت IP به کشور/موقعیت ثبت‌شده در پایگاه داده |
| State | Snapshot جاری داده‌ها |
| History | سوابق رویدادها و اندازه‌گیری‌ها |
| Subscription | فایل حاوی URIهای قابل دریافت توسط کلاینت |
| Atomic Publish | جایگزینی خروجی کامل بدون نمایش وضعیت نیمه‌کاره |
| Schema | قرارداد ساختار داده |

## ۵. اصل تصمیم‌گیری

در اختلاف بین تعداد زیاد کانفیگ و صحت طبقه‌بندی، صحت طبقه‌بندی اولویت دارد. سامانه نباید برای افزایش تعداد Fixed، آستانه را بدون ثبت نسخه Policy کاهش دهد.
